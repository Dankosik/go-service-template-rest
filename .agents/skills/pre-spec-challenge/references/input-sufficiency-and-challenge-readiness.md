# Input Sufficiency And Challenge Readiness

## Behavior Change Thesis
When loaded for a candidate bundle that feels too thin, this file makes the model route to framing or targeted research instead of inventing challenge questions from missing decisions.

## When To Load
Load this when candidate synthesis might be too thin to challenge, evidence is missing, or the pass is drifting into blank-page design.

## The Move
Challenge only after the bundle names a problem frame, candidate decisions, constraints, assumptions or open questions, and at least one seam whose answer could change planning. Route thinness precisely: an absent problem, success criterion, or user-visible outcome returns to framing; a list of options with no chosen direction returns to synthesis or research; a single missing fact — mixed-version client behavior, tenant boundary evidence, cache invalidation precedent — reopens one specialist lane. Name the exact missing decision or evidence and the smallest unblocking route rather than asking whether detail suffices, and classify the missing piece as product policy, repository fact, or specialist evidence, since each routes differently. A low-impact, reversible assumption with a missing link is still challengeable. This checkpoint is neither `spec-clarification-challenge` nor the independent specification review gate; the orchestrator only needs to know whether challenge can proceed.

## Imitate
- "Which candidate decision would change if the retry assumption is false, and what evidence currently supports it?"
  - Copy the way the question ties sufficiency to a decision fork, not generic completeness.
- "Is the missing constraint product policy, repository fact, or specialist evidence?"
  - Copy the routing split: different missing facts need different next actions.
- "If no candidate decision is present, should this return to synthesis instead of challenge?"
  - Copy the refusal to turn challenge into primary design.

## Reject
- "What are all the open questions?"
  - Invites a broad intake list instead of a planning-risk challenge.
- "Ask the user whether the repository supports mixed-version clients."
  - The fact should be researched from repo evidence or deployment docs, not pushed to the user.
