# Technical Design Review Stage

Mode: lean local
Status: implemented and validated

## Intent

Make technical design review a first-class mandatory stage whenever separate technical design depth is triggered. A task-local design bundle should not be treated as planning-ready until a distinct, read-only technical design review gate has run and the orchestrator has reconciled its findings.

## Scope / Non-goals

In:
- repository workflow authority docs;
- subagent contract and brief templates;
- canonical workflow/design/planning/status skills under `.agents/skills/`;
- canonical design-integrator agent routing under `.codex/agents/`;
- runtime mirrors generated by existing sync commands;
- task-local closeout evidence for this amendment.

Out:
- changing Go runtime code, API contracts, database schema, CI policy, or deployment behavior;
- making direct-path work create design-review artifacts;
- making compact lean-local `spec.md` design answers require subagents by default;
- making review agents write-capable or decision-authoritative.

## Behavior / Contract Delta

ADDED:
- Technical design review is mandatory when separate design depth is triggered, including one-file `design/overview.md` and split `design/` bundles.
- The review runs after technical design and before planning.
- Full-orchestrated triggered design uses a dedicated technical-design-review stage with at least one read-only review lane unless an explicit scoped-down local-review rationale is recorded.
- Planning may start only after review findings are reconciled to `PASS` or `CONCERNS` with named accepted risks and proof obligations.
- Review records name the reviewed packet, reviewer or lane, scope, classified findings, orchestrator resolution, gate result, and planning-input obligations.

MODIFIED:
- Technical-design sessions produce review-ready design, not planning-ready design.
- Planning-entry checks must verify the technical design review gate when separate design artifacts exist.
- Workflow status must report missing technical design review as a blocker to implementation readiness.

REMOVED:
- Any wording that allows separate technical design to hand directly to planning without a distinct review checkpoint.

## Decisions

- D1: Technical design review is a mandatory pre-planning gate whenever separate task-local design depth is triggered.
- D2: Direct path remains unaffected because it has no separate technical design stage.
- D3: Lean local with only `spec.md` `Compact Design` continues to use inline `Risk Challenge`; this is not a separate technical design review stage.
- D4: Lean local with a separate `design/overview.md` must record a technical design review checkpoint before `tasks.md`; the review may be a local read-only orchestrator pass if no formal subagent trigger exists.
- D5: Full orchestrated triggered design must route a distinct technical-design-review stage, normally through at least one independent read-only lane such as `design-integrator-agent` or the relevant specialist review/spec lane. More lanes are used when independent design-risk domains are real.
- D6: Review output is advisory evidence. The orchestrator owns fan-in, final decisions, accepted risks, reopen targets, and artifact updates.
- D7: Review gate status is `PASS`, `CONCERNS`, or `FAIL`. `CONCERNS` must name accepted risks and proof obligations. `FAIL` blocks planning and reopens technical design or specification.
- D8: A missing required design review discovered during planning, implementation, or validation reopens the owning earlier phase instead of being patched over later.
- D9: Review findings are classified by planning impact (`blocks_planning`, `reopens_design`, `reopens_spec`, `accepted_risk_candidate`, `proof_obligation`, or `record_only`) so planning cannot hide unresolved review blockers inside optimistic tasks.

Ownership / source of truth:
- `AGENTS.md` owns the invariant that technical design review is mandatory after triggered design and before planning.
- `docs/spec-first-workflow.md` owns gate mechanics, artifact placement, and lean/full differences.
- `docs/subagent-contract.md` and `docs/subagent-brief-template.md` own reusable lane rules and brief shape.
- `technical-design-session` owns design production and review-ready handoff.
- `planning-session` and `planning-and-task-breakdown` own planning-entry enforcement.
- `workflow-status` owns read-only status reporting for the missing gate.
- `design-integrator-agent` owns the default integrated design-review lane.

Sequence / failure behavior:
- A task classifies shape and decides whether design depth is triggered.
- Technical design creates or updates the design bundle and records that the next stage is technical design review.
- Technical design review inspects the approved `spec.md`, design bundle, conditional artifacts, and relevant repository architecture context.
- The orchestrator reconciles review findings. `PASS` or `CONCERNS` may route to planning; `FAIL` reopens technical design or specification.
- Planning refuses to write or approve `tasks.md` from separate design artifacts when the required review gate is missing or blocked.

## Risk Challenge

1. What irreversible or externally visible decision could be wrong?
   Answer: Making review mandatory for every compact design note would undo lean-local simplification. The change limits the mandatory stage to separate design depth and keeps compact `spec.md` design under inline `Risk Challenge`.
2. What hidden invariant or owner could this break?
   Answer: Subagents must remain read-only and advisory. The change makes the review gate mandatory, not reviewer authority mandatory; orchestrator reconciliation remains final.
3. What fresh proof will make the completion claim trustworthy?
   Answer: Targeted reads plus `rtk make agents-sync`, `rtk make skills-sync`, `rtk make agents-check`, `rtk make skills-check`, and `rtk git diff --check`.
