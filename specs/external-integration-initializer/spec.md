# Scaffold one explicit outbound integration without inventing provider semantics

status: ready

Problem: A derived service can already retain bounded outbound HTTP, native
gRPC, and OAuth 2.0 client-credentials capabilities, but adding one concrete
provider still repeats contract generation, typed configuration, composition,
cleanup, documentation, and drift proof. Hand-written copies can bypass the
retained transport and secret boundaries. The initializer must remove that
mechanical work without pretending it can infer business mapping, provider
semantics, or operation retry safety.

## Outcome, scope, and actors

`make integration-init` adds one named, fixed-authority outbound dependency to
an already initialized service. Its actor is a service developer who already
owns a local provider contract and has selected the required template
capabilities through `make template-init`.

The command is build-time only. It performs no network, provider, deployment,
credential, database, or other external write. A service that never invokes it
retains no integration-specific runtime code, configuration, documentation, or
dependency.

Version 1 supports:

- an HTTP client generated from one repository-owned OpenAPI contract; or
- a gRPC client generated from one repository-owned Protobuf contract;
- unauthenticated transport or the retained OAuth 2.0 client-credentials
  capability; and
- external or deployment-owned private HTTPS resource targets for HTTP.

It does not add an inbound integration, webhook receiver, provider SDK,
capability manifest framework, generic integration registry, or generic
business port.

## Invocation contract

The accepted command shape is:

```bash
make integration-init \
  NAME=billing \
  TRANSPORT=http \
  CONTRACT=api/external/billing/openapi.yaml \
  TARGET=external-https \
  AUTH=oauth2-client-credentials
```

or:

```bash
make integration-init \
  NAME=identity \
  TRANSPORT=grpc \
  CONTRACT=api/proto/external/identity/identity.proto \
  AUTH=oauth2-client-credentials
```

Every shown variable is required except that `TARGET` is required only for
HTTP and is rejected for gRPC. Unknown variables owned by this command are
rejected rather than ignored.

| Input | Accepted behavior |
| --- | --- |
| `NAME` | One lower-case ASCII Go package identifier that is not a keyword. It is used verbatim; the command never silently normalizes it. |
| `TRANSPORT` | Exactly `http` or `grpc`. |
| `CONTRACT` | A tracked, committed, regular, non-symlink file that cannot escape the repository. HTTP requires `api/external/<NAME>/openapi.yaml`, validated and generated by the repository's pinned OpenAPI tools. gRPC requires a `.proto` entrypoint below `api/proto/external/<NAME>/`, inside the existing Buf module. These are new initializer-owned source locations, not paths already covered by current generation checks. The command never fetches or rewrites the contract. |
| `TARGET` | For HTTP, exactly `external-https` or `private-https`. The runtime authority remains configuration, not an initializer argument. gRPC rejects this initializer variable and uses the constrained runtime target described below. |
| `AUTH` | Exactly `none` or `oauth2-client-credentials`. There is no implicit authentication default. OAuth token acquisition in v1 uses one fixed external HTTPS token authority. |

The command requires a clean Git worktree and a present `template.lock`. This
is the deliberate v1 transaction boundary: the contract has an immutable input
identity, the initializer never has to merge with unrelated edits, and a failed
run can restore only its own clean-start delta. Dirty-worktree composition is
not supported.

## Retained-capability preconditions

The initializer reads the already resolved choices; it never re-enables a
profile or reconstructs files physically removed by `make template-init`.

| Requested behavior | Required retained choice |
| --- | --- |
| `TRANSPORT=http` | `outbound_http = "bounded"` |
| `TRANSPORT=grpc` | `grpc = "enabled"` |
| `AUTH=oauth2-client-credentials` | `outbound_auth = "oauth2-client-credentials"` |

A missing or conflicting choice fails before any write and names the exact
required choice. Absence of `template.lock`, unresolved template profile
sources or markers, an invalid contract, a path collision, or a changed locked
integration identity also fails before any owned output is replaced.

## Ignored `.env` fail-closed contract

The initializer never takes custody of the repository-root ignored `.env`. On
the first `AUTH=oauth2-client-credentials` invocation whose success would retire
the singleton `outbound_auth` configuration, any filesystem entry at `.env`
fails the invocation before output mutation. The command may observe only that
the path exists. It does not open, source, parse, hash, copy, rename, chmod,
delete, restore, or include the path in its rollback snapshot. The failure names
the path and the manual prerequisite, but not its file type, size, keys, values,
or other contents.

The service developer or operator remains the sole custodian of any sensitive
values in that file. They must preserve or move it outside the initializer's
authority, run the initializer, and then manually map retained values to the
generated named integration inputs before local runtime. Restoring unchanged
legacy `APP__OUTBOUND_AUTH__*` entries is not compatibility input: existing
unknown-key validation rejects them at startup without echoing their values.
The initializer does not retain a singleton alias, infer whether values are
secrets, or migrate values automatically.

`AUTH=none` does not trigger this precondition and leaves `.env` outside command
authority. After the first OAuth integration is recorded, a same-identity no-op
or generated-only refresh neither requires `.env` to be absent nor gains
authority over it. Initial rejection leaves the clean-start repository and
`.env` bytes unchanged. An induced initial failure after the absence check
restores only initializer-owned repository bytes and leaves `.env` absent. An
induced refresh failure restores generated-only repository bytes and leaves any
present `.env` byte-identical.

## Generated result

One successful invocation leaves a compiling, formatted scaffold with these
observable owners:

- the supplied contract remains the canonical, manually owned source;
- generated client types are derived only from that contract and are covered by
  the repository's generated-drift check;
- one integration-specific concrete adapter owns the generated client, target
  construction, authentication binding, and later provider operation methods;
- one integration-specific typed configuration section owns the fixed runtime
  target and only the values required by the selected transport and
  authentication mode;
- the service composition root constructs the adapter, exposes it for explicit
  feature injection, and registers bounded cleanup for its HTTP idle pool,
  gRPC connection, and OAuth owner as applicable;
- integration documentation records the contract authority, runtime inputs,
  selected trust class, authentication mode, lifecycle, and the manual work
  still required before a business operation is exposed;
- one machine-readable integration record stores the name, transport, contract
  path, target class when applicable, authentication mode, and generator source
  identity; and
- the initializer extends the repository's canonical generation and drift
  entry points to include the new source path, using the already pinned
  OpenAPI or Buf/Protobuf toolchain rather than introducing another one.

Generated files and manual adapter files have disjoint ownership. A repeated
invocation with the same locked identity may refresh generated-only outputs
after a committed contract change, but it never overwrites manual operation
mapping, errors, tests, or documentation edits. With no contract change it is a
no-op. Changing the name, transport, target class, or authentication mode is an
explicit migration and is rejected by v1; there is no automatic remove or
reconfigure command.

The scaffold contains no `TODO`, panic placeholder, fake success, unused
provider response, or operation that business code can call accidentally. It
may expose the concrete adapter for later injection, but only a separately
implemented operation may translate a feature command into a provider request
and a provider result into a domain result.

## Runtime behavior and failure boundaries

- Startup validates every generated config field and rejects unknown, missing,
  empty, or incompatible values before publishing service readiness.
- Construction performs no provider call. The generated dependency does not
  add a generic provider health probe and does not change liveness or readiness
  after successful local construction. Provider criticality belongs to the
  feature operation that adopts it.
- HTTP always uses the retained fixed-authority client. It refuses redirects
  and proxies, pins scheme and authority on every request, and applies the
  selected post-DNS public or private address policy. A caller-controlled or
  per-request destination is unsupported. `private-https` additionally requires
  a non-empty deployment-owned private DNS suffix in the integration's typed
  runtime config; the base URL host must be strictly below that suffix, and the
  retained dial gate accepts only private resolved addresses. The suffix field
  is absent for `external-https`.
- gRPC runtime config accepts exactly one `dns:///hostname:443` logical backend
  with no user info, IP literal, path beyond the resolver form, query, or
  fragment. TLS uses system roots and verifies that hostname. The retained
  gRPC client owns DNS resolution, reconnects, default `pick_first` balancing,
  transparent transport retries, and finite shared header/message bounds; it
  disables resolver-supplied service config, so the scaffold adds no configured
  RPC retry or load-balancing policy. Plaintext, custom roots, mTLS, another
  resolver scheme, and caller-controlled targets are outside v1.
- OAuth credentials are attached only by the retained credential owner. The
  generated adapter receives no token source or raw token API. The client
  secret is environment-only; non-secret defaults may use the repository's
  normal config sources.
- Shared HTTP or gRPC telemetry may identify the bounded integration name,
  transport, operation, result class, and latency. Contract data, target URLs,
  tenant or user identifiers, credentials, authorization headers, tokens,
  raw provider bodies, and raw provider errors never become logs, spans,
  metrics labels, caller-visible errors, documentation examples, or command
  output.
- Shutdown rejects new credential acquisition, joins bounded in-flight
  authentication work where applicable, closes the gRPC connection, and closes
  HTTP idle connections within the service's existing shutdown owner.
- Transport unavailability, cancellation, and deadline expiry remain distinct
  from a provider business rejection. No raw error is promoted into a domain or
  client-visible result.

The initializer does not generate retries, hedging, circuit breaking, a
readiness probe, or a retry policy enum. HTTP and gRPC operation methods added
later must own a finite context budget, response parsing and bounds, safe error
mapping, and any retry eligibility. An HTTP verb, Protobuf option, idempotency
key header, or generated method name is insufficient proof that a mutation is
safe to repeat.

## Security dispositions

Outbound egress:

```text
disposition: constraint_only
decision_or_constraint: generated HTTP uses one retained fixed-authority target class and an explicit private suffix when selected; generated gRPC accepts only one operator-owned dns:///hostname:443 backend with system-root TLS and retained grpc-go resolver behavior; dynamic destinations are rejected
forced_consequences: contract and runtime config cannot introduce per-request destinations; HTTP deny paths, private-suffix binding, gRPC target syntax, and TLS hostname construction remain in focused proof
proof_or_gap: assert rejected scheme, authority change, redirect, proxy path, resolved address class, absent or mismatched private suffix, invalid gRPC resolver or authority, dynamic target, and missing TLS credentials as applicable
blocker: none
strongest_rejected_alternative: none
rejection_reason: none
reopen_owner_or_condition: Security Decision when caller-controlled destinations, proxies, custom roots, plaintext, mTLS, or discovery become required
```

Secrets and disclosure:

```text
disposition: constraint_only
decision_or_constraint: secrets are environment-only and raw credentials, provider bodies, targets, and provider errors cannot cross generated output or observability boundaries
forced_consequences: generated config, fixtures, docs, errors, logs, spans, metrics, and command output require negative leak proof
proof_or_gap: inject distinct canaries and assert absence at every reachable sink; run the repository secret scan over generated examples and fixtures
blocker: none
strongest_rejected_alternative: none
rejection_reason: none
reopen_owner_or_condition: Security Decision when a new credential type, secret store, disclosure sink, or reader class is introduced
```

Ignored `.env` custody:

```text
disposition: decision
decision_or_constraint: fail before mutation when the first OAuth initializer would retire singleton config and any repository-root .env entry exists; observe path presence only and leave all value migration to its developer or operator custodian
forced_consequences: no automatic read, rewrite, backup, deletion, restoration, or singleton alias; unchanged legacy keys fail current startup unknown-key validation; AUTH=none and post-migration refresh never take .env custody
proof_or_gap: use distinct canaries to prove initial rejection is pre-mutation and non-disclosing, initial failure with no .env restores owned bytes without creating it, and same-identity refresh leaves a present .env byte-identical and absent from command output and generated artifacts
blocker: none
strongest_rejected_alternative: automatically parse or rewrite the ignored file, or preserve a singleton runtime alias for the first named integration
rejection_reason: automatic migration would make a build-time scaffold owner read and restore potentially sensitive shell bytes, while an alias makes stale singleton authority ambiguous once integrations are independently named
reopen_owner_or_condition: Specification and Security Decision when a named adopter requires automatic ignored-file migration or legacy singleton compatibility
```

## Deliberately unchanged behavior and non-goals

- `make template-init` remains the only owner of template profile selection,
  physical profile removal, module identity, and the base `template.lock`.
- Business behavior remains in `internal/<feature>` and does not import a
  concrete transport or generated provider client.
- Provider operation names, request/response mapping, domain errors,
  idempotency, retry eligibility, partial-success meaning, reconciliation, and
  effect finality remain service-owned work after initialization.
- The initializer does not infer an OpenAPI operation subset, Protobuf service
  subset, OAuth scopes, audience, resource, provider base URL, dependency
  criticality, timeout value, response-size value, concurrency limit, or
  telemetry business vocabulary.
- It does not create a generic `Integration`, `Provider`, `Client[T]`, factory,
  registry, plugin API, manifest DSL, or provider-agnostic error taxonomy.
- It does not add a dependency to `go.mod`; it reuses the retained runtime
  packages, standard library, and repository-owned OpenAPI/Protobuf generators.
- It does not contact a live provider or claim provider compatibility,
  authentication success, contract conformance, production readiness, or
  business-operation correctness.

## Success criteria and proof expectations

The Specification is satisfied when the smallest deterministic fixture matrix
proves all of the following:

1. One HTTP and one gRPC invocation add their previously unsupported source
   locations to the canonical generation/drift owners and generate compiling,
   formatted output with the pinned OpenAPI or Buf/Protobuf toolchain and
   retained transport.
2. OAuth selection binds the retained credential owner without exposing its
   secret or token API; `AUTH=none` leaves no auth-specific config or code.
3. Missing retained capabilities, invalid or escaping contract paths, symlinks,
   invalid names, unknown choices, collisions, dirty worktrees, and changed
   locked identities fail before output mutation. A first OAuth migration with
   any root `.env` entry does the same without inspecting its contents.
4. An induced generation or validation failure restores the clean-start
   repository bytes, while a same-identity repeat is a no-op and a committed
   contract change updates generated-only bytes. Initial and refresh fixtures
   also prove the `.env` absence or bytes from command entry are unchanged.
5. After the initializer extends their inputs, the repository's canonical
   generated-drift and aggregate checks detect stale external client code.
   Generated output also passes project-structure, formatting, compile, focused
   transport-denial, secret-scan, and initializer contract checks.
6. A generated local fake exercises only client construction, one successful
   bounded exchange, and one sanitized failure. It does not emulate provider
   business semantics or require a live endpoint.
7. Before and after invocation, unrelated template capabilities and manually
   owned paths are byte-identical.
8. Distinct sensitive canaries from an operator-owned `.env` are absent from
   initializer output, errors, rollback material, generated files,
   documentation, logs, and test diagnostics. Restoring an unchanged legacy
   fixture after successful first OAuth initialization proves startup rejects
   the retired key names without disclosing their values; a manually mapped
   named fixture proves the accepted local-runtime path.

These checks establish scaffold integrity and negative safety boundaries. They
do not establish a concrete provider operation's semantics, retry safety,
runtime availability, or production compatibility; those claims require the
operation's own Specification, design, and proof.

## Risks, assumptions, and reopen conditions

- Current authority is the repository at `8967a4ac06d4fce0515703b15ffa5db35e5378ae`
  plus the inspected dirty tree. Uncommitted HTTP-client, OAuth, initializer,
  and workflow edits are evidence, not accepted implementation inputs. Refresh
  this Specification if their accepted contracts change before Technical
  Design.
- Requiring a clean worktree and a committed local contract avoids a
  multi-file merge and rollback protocol. Reopen Specification only when a
  named adopter demonstrates that a separate contract commit is not workable;
  then define the exact dirty-path ownership and recovery contract before
  relaxing the precondition.
- OAuth token acquisition is limited to external HTTPS in v1. A private token
  authority, provider-specific signing, API key, workload identity, custom CA,
  or mTLS reopens Security and System / Integration Design.
- Multiple integrations are allowed only as independent named invocations with
  disjoint config, generated, adapter, documentation, and lock ownership.
  Observed repeated code does not by itself justify a generic registry or
  manifest.
- The ignored `.env` boundary deliberately requires a manual custody step for
  the first OAuth migration. Reopen Specification and Security Decision only
  when a named adopter requires the initializer itself to migrate that file;
  then define its shell grammar, concurrent-change detection, permissions,
  atomic replacement, backup custody, and recovery before granting read or
  write authority.
- A contract that requires a provider SDK, custom code generator, dynamic
  endpoint, streaming-specific lifecycle, or unsupported authentication fails
  closed and reopens Specification rather than silently emitting a weaker
  scaffold.

Definition is ready when independent Specification Review finds no surviving
material behavioral divergence. The next owner is System / Integration Design;
it must select the command implementation, exact generated/manual file split,
generator registration, config and bootstrap shape, integration record format,
cleanup composition, and atomic clean-worktree application without adding
behavior excluded here.
