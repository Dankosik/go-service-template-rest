## Proof-boundary decisions

- Unit and HTTP contract tests own exact encodings, parser behavior, registration
  closure, response precedence, bounded mappings, and zero-registration wiring.
  A database would add no observable to those claims.
- PostgreSQL 17 through the digest-pinned `pgtest` harness, configured with
  `track_commit_timestamp=on` for this integration family, owns reservation
  arbitration, row-lock visibility, caller-transaction atomicity, writer
  reconciliation, exact commit epoch, expiry, and cleanup. Mocks are rejected for
  those claims because they can pass without the selected lock or transaction.
- One synthetic opted operation supplies decision-neutral small bounds and codecs.
  Its values are test inputs, not template defaults or adopter readiness evidence.
- Commit ambiguity is proved at two complementary boundaries: the existing real
  PostgreSQL `postgres.InTx` lost-result test pins `ErrCommitUnknown`, and the new
  store integration family drives every writer reconciliation state. A timing-
  sensitive socket cut is not used as a substitute for branch proof.
- No generic end-to-end endpoint exists in the template. The reusable store and
  envelope are therefore composed with a synthetic adapter; the first adopting
  endpoint must additionally prove its own feature transaction and selected
  downstream recovery at its real boundary.
- Container proof keeps two claims separate. The existing health-only initialized
  image owns positive migration/image lifecycle only. A distinct disposable
  OIDC-enabled initialized checkout receives
  `scripts/ci/fixtures/postgres-http-idempotency-active.patch`, is built once, and
  owns active missing-schema, non-writer, and commit-timestamp rejection before
  OIDC initialization. Positive active composition is local real-PostgreSQL
  bootstrap proof; positive active production-image proof remains the adopter's
  authenticated canary against its real issuer.
- Commands naming new tests are post-implementation commands. A current `no tests
  to run` result is a proof gap, not a pass.

## Deterministic controls

- Concurrent PostgreSQL schedules synchronize on writer state: backend PID,
  `pg_stat_activity`, `pg_blocking_pids`, committed rows, and owned channels.
  Elapsed time is only an outer hang diagnostic.
- Two independently constructed Store instances represent two replicas; one Store
  with many goroutines represents one replica. Test-only PostgreSQL trigger gates,
  distinguished by `application_name`, hold the first insert after it becomes
  visible to lock arbitration so the cross-replica unique-index wait is forced
  without a production hook.
- `testing/synctest` proves that one non-resetting `W_in_progress` context covers
  coordinator wait and stage transitions. Real PostgreSQL cases separately hold
  every pool connection or row lock and prove that the same context cancels pool
  acquisition and writer work before feature execution.
- Process-death cases run a helper subprocess, identify its PostgreSQL backend,
  and kill the process at an owned IPC event. The after-commit case holds a
  parent-owned adapter gate between definite transaction return and renderer entry
  while a PostgreSQL trigger holds epoch materialization; the parent independently
  confirms durable state before SIGKILL. Every case observes backend/lock
  disappearance and joins every successor. Closing an in-memory Store is not
  accepted as death proof.
- Durable oracles use an independent writer connection to count the feature row,
  idempotency row/result, and optional outbox row after commit or rollback.
- Retention cases derive boundary timestamps from `clock_timestamp()` in the
  writer. Every duration passed to PostgreSQL is normalized by ceiling to whole
  microseconds, including a positive sub-microsecond value; rows remain retained
  through the exact normalized writer-time horizon. Row locks force request-first
  and cleanup-first orders for both result stripping and finite-guard deletion; no
  application clock or sleep decides eligibility.
- Terminal telemetry uses the two mutually exclusive finality owners: a final
  admission rejection in the envelope, or one admitted endpoint/application final
  return after transaction and reconciliation. A reservation, `Acquire`, or
  `Complete` is never a terminal request outcome. Request-discovered epoch loss
  publishes the first Store terminal error before returning its 503 classification;
  the already-running supervised maintenance task consumes the one wakeup without a
  cadence tick and begins the ordinary drain.
- Redaction cases inject unique sentinel key, authority, fingerprint, result, SQL,
  and database-error values, then inspect rendered Problems, captured logs/spans,
  metric attributes, and exported series.
