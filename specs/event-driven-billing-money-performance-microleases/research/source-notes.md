## External Sources

| Source | Type | Relevant evidence | GonkaGate implication |
| --- | --- | --- | --- |
| O'Neil, "The Escrow Transactional Method" - https://www.ics.uci.edu/~cs223/papers/p405-o_neil.pdf | Paper | Escrow addresses hot aggregate fields by allowing bounded concurrent increments/decrements while preserving constraints. | Microleases are best treated as escrowed USD spend rights, not cached balance. |
| "Extending Eventually Consistent Cloud Databases for Enforcing Numeric Invariants" - https://arxiv.org/abs/1503.09052 | Paper | Bounded counters adapt escrow ideas to partition numeric rights across replicas while preserving numeric invariants. | Per-instance/per-shard microleases map to allocated rights; local spend is safe only while local rights are sufficient. |
| "Coordination Avoidance in Database Systems" - https://arxiv.org/abs/1402.2237 | Paper | Coordination-free execution is safe only for invariant-confluent operations; otherwise coordination is needed. | "Available balance never negative" needs prior coordination or preallocated rights before independent local debits. |
| Redis rate limiter docs - https://redis.io/docs/latest/develop/use-cases/rate-limiter/ | Official docs | Redis supports centralized fast rate limiters with `INCR`, `EXPIRE`, strings/hashes/sorted sets, and Lua for atomic read-decide-update. | Redis is credible for a shared limiter or token bucket, but source does not make it durable money authority. |
| Redis persistence docs - https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/ | Official docs | RDB can lose recent writes; AOF/RDB choices trade durability, resources, and recovery. No persistence loses data on restart. | Redis loss must not mint or lose customer-money authority. Treat Redis as rebuildable limiter/cache unless a later spec explicitly accepts bounded write-off risk. |
| Redis replication docs - https://redis.io/docs/latest/operate/oss_and_stack/management/replication/ | Official docs | Redis replication is asynchronous by default; `WAIT` reduces loss probability but does not make Redis a strongly consistent CP system. | Redis acknowledged writes can still be unsafe for exact prepaid money during failover. |
| Envoy local rate limit docs - https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/local_rate_limit_filter | Official docs | Local rate limiting applies a token bucket per Envoy process or connection and returns rate-limited responses when tokens are exhausted. | Local buckets are useful for fast per-instance throttling and as a cache over reserved lease capacity, not global money authority. |
| Envoy Gateway rate limiting docs - https://gateway.envoyproxy.io/docs/concepts/rate-limiting/ | Official docs | Global limits coordinate across instances through an external rate-limit service; local limits are independent per instance. Both may be combined. | Strict fleet-wide spend requires global/durable authority or preallocated per-instance rights; local-only limits can over-allow across replicas. |
| Envoy rate limit service docs - https://www.envoyproxy.io/docs/envoy/latest/configuration/other_features/rate_limit.html | Official docs | Envoy global rate limiting depends on an external rate limit service for global decisions. | A global limiter is an external dependency and still needs a durable money source of truth. |
| Apache Kafka producer configs - https://kafka.apache.org/30/configuration/producer-configs/ | Official docs | Producer idempotence avoids duplicate writes from producer retries when required producer settings hold. | Broker producer idempotence is useful for terminal facts, but it does not cover billing DB effects or external execution. |
| Apache Kafka Streams concepts - https://kafka.apache.org/33/streams/core-concepts/ | Official docs | Kafka Streams exactly-once atomically ties input offsets, state stores, and Kafka output topics. | Exactly-once scope is Kafka-integrated processing, not arbitrary Postgres money mutation or upstream API execution. |
| Redpanda transactions - https://docs.redpanda.com/25.3/develop/transactions/ | Official docs | Redpanda supports Kafka-compatible transactions, EOS with idempotent producers, and atomic topic writes when transactions are used. | Redpanda can help terminal pipelines, but billing still needs Postgres inbox/idempotency before offset commit. |
| Redpanda idempotent producers - https://docs.redpanda.com/redpanda-cloud/develop/produce-data/idempotent-producers/ | Official docs | Idempotence deduplicates producer retries within a producer session by producer ID and sequence; manual retries can still duplicate. | Event identity and billing inbox dedupe remain mandatory. |
| Stripe usage recording - https://docs.stripe.com/billing/subscriptions/usage-based/recording-usage-api | Official docs | Meter events may be sent as they occur or in batches; summaries update asynchronously; idempotency identifiers prevent duplicate reporting. | Stripe-style metering supports async terminal accounting, not prepaid admission unless GonkaGate has its own prior reserve/lease authority. |
| Stripe Meter Event Stream changelog - https://docs.stripe.com/changelog/acacia/2024-09-30/usage-based-billing-v2-meter-events-api | Official docs | High-throughput stream supports large event rates through short-lived session tokens and async validation. | High throughput usage reporting is possible, but it remains metering after an event, not a no-overspend gate. |
| Stripe rate limits - https://docs.stripe.com/rate-limits | Official docs | Meter event endpoints have separate rate limits and concurrency/cardinality limits. | External metering APIs still need queueing, retry, and backpressure. |
| Metronome idempotency - https://docs.metronome.com/api-reference/idempotency | Official docs | Usage ingestion dedupes by `transaction_id` for a retention window; API idempotency has conflict behavior. | Terminal usage events need stable transaction IDs and durable duplicate/conflict handling. |
| Metronome send usage events - https://docs.metronome.com/guides/events/send-usage-events | Official docs | Metronome recommends reliable queues and safe retry because ambiguous ingest failures may have partially accepted events. | Proxy/billing terminal flow should use durable queue/outbox and idempotent event ingestion. |
| OpenMeter ingestion docs - https://openmeter.io/docs/metering/events/how-it-works | Official docs | OpenMeter accepts CloudEvents, writes to Kafka, scales consumers by partitions, deduplicates, and inserts into ClickHouse. | Kafka/ClickHouse are strong for usage metering and aggregation, not the authoritative prepaid balance boundary. |
| OpenMeter ClickHouse write-up - https://openmeter.io/blog/how-openmeter-uses-clickhouse-for-usage-metering | Engineering write-up | OpenMeter pre-aggregates usage into windows and uses DLQ patterns for failed records. | Aggregation windows and DLQ are useful for analytics and terminal metering, not first admission. |
| DynamoDB item docs - https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/WorkingWithItems.html | Official docs | Atomic counters are not idempotent and are inappropriate when overcount/undercount cannot be tolerated; conditional writes can be idempotent. | Generic counters are poor money gates. Conditional writes/transactions are closer to money-safe admission. |
| Firestore distributed counters - https://firebase.google.com/docs/firestore/solutions/counters | Official docs | Sharding counters raises write throughput but makes reads more expensive and rollups stale. | Sharded counters fit telemetry/projections, not exact current prepaid funds unless each shard is a reserved right. |
| AWS transactional outbox - https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html | Official docs | Outbox resolves database/message dual-write inconsistency; consumers still need idempotency and ordering care. | Billing outbox and proxy terminal outbox are required if events follow money or execution state changes. |
| Debezium outbox event router - https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html | Official docs | Outbox SMT captures outbox-table inserts and routes them as events. | Confirms a known implementation shape for DB-owned event publication, though runtime choice remains later-phase design. |
| Idempotent consumer pattern - https://microservices.io/patterns/communication-style/idempotent-consumer.html | Pattern reference | At-least-once brokers can invoke consumers repeatedly; durable processed-message IDs prevent duplicate effects. | Billing terminal inbox must dedupe by stable event/business identity inside the money transaction. |

## Repository Evidence

| Source | Evidence | Research implication |
| --- | --- | --- |
| `docs/critical-billing-context.md` | Billing owns USD ledger, available/reserved/settled amounts, durable idempotency, stored outcomes, write-off/reversal, and reconciliation. Redis may be cache/load-shed only, not money correctness store. | New performance design must keep durable money authority in billing unless it explicitly accepts platform write-off exposure. |
| `docs/PRD.md` | Paid usage should reserve before execution; finalization and write-off are idempotent; paid usage fails closed when billing is unavailable; raw prompts, outputs, SSE chunks, API keys, tokens, DSNs, and payment secrets are forbidden in telemetry/artifacts. | Research and future spec must preserve fail-closed and privacy constraints. |
| `docs/repo-architecture.md` | Async work needs explicit app/infra/lifecycle ownership; business endpoints need real security; generated contracts are source-of-truth inputs. | Microlease/event work will require later technical design before implementation. |
| `api/openapi/service.yaml` | Current billing OpenAPI has only ping, health, readiness, and metrics with public system posture. | Business money contracts do not yet exist in this repo. |
| `env/migrations/000003_billing_money_core.up.sql` | Current schema has account balances, idempotency records, operation outcomes, usage holds, terminal outcomes, ledger entries, imports, reconciliation, and audit primitives with money constraints. | Existing Postgres primitives are a strong base for lease/microlease authority, but not yet microlease-specific. |
| `internal/infra/postgres/queries/billing_money_core.sql` | Current queries include balance locks, idempotency locks, usage hold locks, ledger insertion, and reconciliation claim surfaces. | Current repo already prefers durable row-lock/idempotency patterns for money. |

| `specs/event-driven-billing-money-architecture/design/overview.md` | Existing design selects proxy allocator owners/fences, protected HTTP issuance, durable child debit allocation, Redpanda terminal facts, checkpoint/close proofs, and admission controls. | Microlease specification should decide whether to keep durable child debit per request or accept bounded memory/Redis leakage under stricter controls. |
| `specs/event-driven-billing-money-architecture/workflow-plans/technical-design-review.md` | Existing technical-design review passed the lease packet and carried planning obligations for proxy durable allocator, pricing evidence, event contracts, rollout, and privacy proof. | New specification should explicitly state whether it preserves, narrows, or reopens those obligations. |
