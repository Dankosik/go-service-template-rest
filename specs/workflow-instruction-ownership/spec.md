# Workflow Instruction Ownership

Mode: lean local
Status: implemented and validated

## Intent

Clean up repository workflow instructions so each instruction type has one canonical ownership layer:

- `AGENTS.md` remains the compact repository authority.
- `docs/spec-first-workflow.md` remains the stable router.
- `docs/spec-first-workflow/phases/*.md` own phase-local execution rules.
- `docs/spec-first-workflow/shared/*.md` own shared mechanics.
- `.agents/skills/*` own reusable agent method and session behavior, without duplicating repository authority.

This change is about instruction architecture only. It does not change runtime Go service behavior.

## Scope / Non-goals

In:

- Canonical workflow docs under `docs/spec-first-workflow.md`, `docs/spec-first-workflow/phases/`, and `docs/spec-first-workflow/shared/`.
- Repository authority text in `AGENTS.md`.
- Canonical workflow skills under `.agents/skills/`.
- Skill mirrors regenerated from `.agents/skills` with the repo sync target.
- A new task-local bundle under `specs/workflow-instruction-ownership/`.

Out:

- Runtime Go code, APIs, migrations, generated service artifacts, OpenAPI, SQLC, Docker, and deployment behavior.
- Rewriting closed historical bundles such as `specs/workflow-simplification/`.
- Treating the historical root `tasks.md` as the active implementation handoff.
- Manual edits to `.claude/.gemini/.github/.cursor/.opencode/skills` mirrors.
- `.codex/agents` or `.claude/agents`, unless validation reveals existing drift.

## Behavior / Contract Delta

ADDED:

- A task-local decision record and ledger for this instruction-ownership cleanup.
- Explicit canonical ownership wording in shared workflow docs and affected skills.
- Planning skills route completed ledgers to `task-review-readiness` instead of approving implementation readiness themselves.

MODIFIED:

- `AGENTS.md` keeps hard authority and points detailed mechanics to phase/shared docs.
- `docs/spec-first-workflow.md` points execution-shape triggers back to `AGENTS.md` and keeps router-only wording.
- `shared/artifact-model.md` records where hard decision rules live instead of restating them as a second authority.
- Session skills reference `shared/subagents-and-handoff.md` for the exact `Subagent authorization:` line and handoff prompt mechanics.

REMOVED:

- Duplicate full `Subagent authorization:` prompt text from workflow skills.
- Planning-skill claims that the planning session itself approves task-ledger review or implementation readiness.

## Decisions

- D1: `AGENTS.md` owns hard repository policy: precedence, role boundaries, global gates, trigger matrix, non-negotiable subagent/read-only rules, no-duplication rule, target-state rule, dependency/OSS diligence, Pattern Fit Diligence, focused responsibility, and session boundary.
- D2: `docs/spec-first-workflow.md` owns only stable navigation: loading order, execution-shape summary, phase read matrix, router guardrails, and short anti-pattern pointers.
- D3: `docs/spec-first-workflow/shared/artifact-model.md` owns artifact layout, artifact status vocabulary, workflow-control ownership, and where hard decisions are recorded.
- D4: `docs/spec-first-workflow/shared/subagents-and-handoff.md` owns reusable subagent gate mechanics, resume order, the exact `Subagent authorization:` line, and chat-only handoff prompt rendering.
- D5: Phase files own phase-local inputs, outputs, stop rules, artifact shape, verdict meanings, and reopen targets. They must not repeat global invariants unless a short pointer prevents misuse.
- D6: Skills own role/session/method behavior, context selection, evidence discipline, examples, and tool-selection behavior. They must reference `AGENTS.md`, router, phase docs, and shared docs instead of restating repo-wide policy or full phase templates.
- D7: `planning.md` owns draft `tasks.md` authoring only. `task-review-readiness.md` is the only canonical task-ledger review and implementation-readiness approval gate.
- D8: `.agents/skills` is the canonical skill source. Runtime skill mirrors are regenerated by `rtk make skills-sync` and then checked with `rtk make skills-check`.

Ownership / source of truth:

- Manual edits happen only in canonical sources: repository docs and `.agents/skills`.
- Mirrored skill directories are derived output from `.agents/skills`.
- `.codex/agents` is out of scope, so `agents-sync` is not expected.

Sequence:

1. Create this spec and the task ledger.
2. Patch docs from the top of the ownership stack downward.
3. Patch canonical workflow skills to reference the owning docs.
4. Regenerate skill mirrors.
5. Run targeted duplication checks and repo-owned validation.
6. Update this bundle with closeout evidence.

Failure behavior:

- If validation shows skill mirror drift, run `rtk make skills-sync` again and inspect the generated diff.
- If `agents-check` fails without `.codex/agents` edits, report existing agent mirror drift separately instead of editing agent sources opportunistically.
- If a grep proof shows remaining duplicate authority, repair the owning source or convert the duplicate to a reference.

## Risk Challenge

1. What irreversible or externally visible decision could be wrong?
   Answer: The main risk is weakening workflow gates by moving hard requirements out of the files agents actually load.
2. What hidden invariant or owner could this break?
   Answer: Planning could continue approving implementation readiness if skills keep stale post-ledger-review wording; subagent prompts could omit the required authorization line if every copy is removed without a canonical pointer.
3. What fresh proof will make the completion claim trustworthy?
   Answer: `rtk make skills-sync`, `rtk make skills-check`, `rtk make agents-check`, targeted grep checks for duplicated authorization/readiness wording, and `rtk git diff --check`.

Gate: PASS

Subagent gate: local_only
Rationale: the user supplied the approved ownership model and implementation plan; the remaining work is deterministic docs/skills normalization plus mirror validation. The active subagent tool requires explicit user authorization before spawning, and the prompt did not authorize delegation. No unresolved product, API, runtime, data, security, delivery, or Go-code decision remains where an independent lane could change the accepted target state. Reopen fan-out if a patch introduces a new workflow policy choice rather than moving or referencing an already-approved rule.

Dependency / OSS Due Diligence: not applicable. No runtime dependency, external library, custom infrastructure, or helper abstraction is introduced.

Pattern Fit Diligence: not applicable. This is an instruction ownership cleanup using the repository's existing spec-first artifact model, not a new architecture or workflow pattern.

Specification review: PASS, local-only.

Technical design review: not expected.
