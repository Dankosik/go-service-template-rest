# Multi-Challenger Spec Clarification

Mode: lean local
Status: approved after multi-lens challenge reconciliation

## Intent

Make formal `spec-clarification-challenge` stronger by turning it from a mostly single-challenger gate into a lens-based multi-challenger fan-out when the work is full-orchestrated, protected-domain, high-risk, or explicitly asks for broad independent challenge.

The goal is better spec quality before approval: more independent approval questions, more corner cases, better cross-domain pressure, and fewer single-model blind spots.

## Scope / Non-goals

In:
- repository workflow authority docs;
- subagent contract and brief templates;
- canonical workflow/challenge skills under `.agents/skills/`;
- canonical challenger agent routing under `.codex/agents/challenger-agent.toml`;
- runtime skill mirrors generated by the existing sync flow;
- runtime agent mirrors generated by the existing sync flow;
- task-local closeout evidence.

Out:
- changing direct-path behavior;
- making subagents write-capable or decision-authoritative;
- requiring five challengers for every lean-local task;
- changing Go runtime code, API contracts, database schema, CI policy, or deployment behavior.

## Behavior / Contract Delta

ADDED:
- Formal spec clarification supports a lens-based multi-challenger fan-out.
- Broad or multi-domain formal clarification for full-orchestrated, protected-domain, high-risk, or user-requested deep-challenge specification work should normally use five independent challenge lenses before `spec.md` approval.
- The orchestrator may add extra specialist challenge lanes when a task has more than five independent approval-risk domains.
- Combined default lenses must be split when one bundled area is independently approval-critical enough that a single lane would hide a real owner decision.
- The orchestrator owns fan-in: dedupe questions, reconcile conflicts, map findings to approval impact, and record final outcomes in `spec.md`.

MODIFIED:
- A formal challenge is no longer documented as inherently one `challenger-agent` lane.
- Single-lane formal challenge becomes an explicit scoped-down exception for narrow formal gates, not the default mental model for broad specs.
- Subagent briefs can include a shared candidate spec bundle plus per-lane lens assignments.
- `spec-clarification-challenge` output records the lens being applied.
- Workflow-control gate status records lanes, lenses, and scoped-down rationale when fewer than the broad default is used.

REMOVED:
- Any wording that implies one generic challenger is sufficient for broad full-orchestrated specification approval by default.

## Decisions

- D1: Use multi-challenger fan-out for broad or multi-domain formal specification clarification when the task is full-orchestrated, protected-domain, high-risk, cross-domain, hard-to-reverse, or explicitly asks for broad/deep challenge.
- D2: Use five default challenge lenses for broad formal clarification:
  - scope and spec coherence;
  - domain invariants and edge cases;
  - architecture ownership and dependency boundaries;
  - API, data, compatibility, and source-of-truth consequences;
  - security, reliability, delivery, and validation proof.
- D3: Allow more than five lanes when a task has additional independent approval-risk domains that cannot be honestly covered by the default lenses.
- D4: Allow fewer lanes only with a recorded scoped-down rationale. One lane is valid only for a narrow formal gate whose approval risk is concentrated in one question.
- D5: Keep every lane read-only, advisory, and single-skill. Multiple challengers improve coverage; they do not share final authority.
- D6: Read-only must be enforced by execution choice. If a lane cannot reliably stay read-only, keep that question in the main orchestrator flow instead of relying on prompt wording.
- D7: Keep lean-local default behavior intact: inline `Risk Challenge` remains enough when no escalation trigger exists. `Risk Challenge=CONCERNS` alone does not trigger formal multi-challenger clarification; it triggers inspection for unresolved scope, ownership, proof, or escalation gaps. User-requested broad challenge or a discovered escalation trigger may route lean work into formal clarification.
- D8: Fan-in is an orchestrator responsibility. Raw lane outputs are evidence; the final approved spec records only reconciled decisions, assumptions, constraints, proof obligations, or reopen targets.
- D9: An unresolved missing-input result or blocker from one lane blocks the relevant approval area until the orchestrator answers it from evidence, records an explicit waiver/accepted risk, or reopens the owning phase.
- D10: Material conflicts between lanes, including blocker-severity conflicts, require explicit orchestrator reconciliation before approval. Rerun clarification only when the reconciled answer materially changes candidate spec decisions or reopens a major seam.
- D11: Lens is metadata, not a new classification vocabulary. Each lane keeps existing `spec-clarification-challenge` classifications, and orchestrator fan-in keeps the existing handoff classifications unless docs/templates are intentionally changed together.
- D12: Workflow-control records use `Lanes:` plus `Lenses:` for multi-challenger gates. Scoped-down formal gates include `Scoped-down rationale:`.
- D13: Authority split is explicit: `AGENTS.md` owns invariants and triggers; `docs/spec-first-workflow.md` owns the high-level trigger/artifact model and broad lens default; `specification-session` owns orchestration procedure; `spec-clarification-challenge` owns per-lens deliverable and classification shape; `docs/subagent-brief-template.md` owns reusable handoff format; `challenger-agent` owns mode routing and read-only agent boundary.
- D14: Validation proves changed source-managed docs, skills, agents, and derived mirrors are in sync for touched surfaces. It does not claim strict deletion/rename detection across all runtime mirrors unless a skill or agent file is removed or renamed.

## Compact Design

Affected surfaces:
- `AGENTS.md`
- `docs/spec-first-workflow.md`
- `docs/subagent-contract.md`
- `docs/subagent-brief-template.md`
- `.agents/skills/specification-session/SKILL.md`

- `.agents/skills/workflow-plan-adequacy-challenge/SKILL.md`
- `.codex/agents/challenger-agent.toml`
- runtime skill mirrors generated by `make skills-sync`
- runtime agent mirrors generated by `make agents-sync`

Ownership / source of truth:
- `AGENTS.md` remains the compact authority for when formal challenge escalates and what cannot be weakened.
- `docs/spec-first-workflow.md` owns the high-level trigger/artifact model and broad multi-lens default.
- `docs/subagent-contract.md` owns lane invariants and fan-in expectations.
- `docs/subagent-brief-template.md` owns reusable handoff shapes.
- `.agents/skills/specification-session` owns specification-phase orchestration procedure.
- `.agents/skills/spec-clarification-challenge` owns per-lens deliverable and classification shape.
- `.codex/agents/challenger-agent.toml` owns challenger mode routing and read-only agent boundary.
- `.agents/skills/*` are canonical skill sources; runtime mirrors are derived.

Sequence / failure behavior:
- The orchestrator classifies shape and decides whether formal clarification is triggered.
- For broad formal clarification, the orchestrator prepares one candidate-spec input bundle and assigns distinct lenses to multiple read-only challenger lanes.
- If a default lens contains multiple independent approval-risk domains for the task, the orchestrator splits that lens into additional lanes or records why one lane is sufficient.
- Lanes run in parallel when independent.
- The orchestrator reconciles all findings before approval.
- If lane findings expose missing decisions, missing input, or unresolved blocker conflicts, the orchestrator reopens the owning phase or records an explicit waiver/accepted risk before approval.
- Workflow-control status records `Lanes:` and `Lenses:` for multi-challenger gates; scoped-down gates record `Scoped-down rationale:`.
- Validation proves changed docs, source-managed skills/agents, and derived mirrors agree for touched surfaces; no runtime tests are required because runtime Go code is out of scope.

## Clarification Reconciliation

This spec was dogfooded with five read-only challenger lanes before closeout:
- scope/spec coherence;
- domain invariants and workflow edge cases;
- architecture ownership and artifact boundaries;
- compatibility and source-of-truth behavior;
- delivery and validation proof.

Reconciled outcomes:
- The mode remains lean local because the implementation is a bounded workflow/tooling-domain docs/skills/agent change with no runtime, public API, data, security, money, reliability, or deploy behavior. The multi-challenger pass was used as a quality gate for this workflow change.
- `Risk Challenge=CONCERNS` alone is not an escalation trigger.
- Default bundled lenses must split when independent approval-risk domains are real.
- Existing classification vocabularies remain stable.
- `spec-document-designer` and `challenger-agent` are in scope.
- Validation must include changed-file scope audit and source-managed mirror sync proof.

## Risk Challenge

1. What irreversible or externally visible decision could be wrong?
   Answer: Making five challengers mandatory everywhere would undo the recent trigger-based simplification. The spec avoids that by limiting the default five-lane behavior to formal broad/high-risk gates and allowing scoped-down rationale.
2. What hidden invariant or owner could this break?
   Answer: Subagents must remain read-only/advisory and each lane must own one question/lens with at most one skill. The change preserves orchestrator fan-in and final decision ownership.
3. What fresh proof will make the completion claim trustworthy?
   Answer: Targeted reads plus `rtk make agents-check`, `rtk make skills-check`, and `rtk git diff --check` after mirror sync.
