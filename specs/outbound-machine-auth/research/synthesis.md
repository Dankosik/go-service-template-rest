# Outbound Machine Authentication Research

status: ready for Specification
Valid as of: 2026-08-11
Boundary: Research only; this note does not select the final architecture or define Specification, Technical Design, Test Design, Planning, or implementation.
Independent Research challenge: PASS; movement to Specification allowed.

## Accepted outcome and stop condition

Research an optional template-init-selected outbound machine-authentication capability, provisionally `OUTBOUND_AUTH=oauth2-client-credentials`, that can authenticate outbound HTTP and gRPC calls from minimal validated configuration while feature code only selects a dependency and invokes its concrete or generated client.

Stop when the current repository baseline, external contracts, candidate families, stable reusable responsibilities, owner-controlled choices, risks, and downstream implications are supported well enough for a fresh Specification session to act without repeating the search.

## Candidate neutral frame

The live decision level is the owner of outbound access-token acquisition and attachment for a fixed service dependency. Candidate families are compared as substitutes only at that level; TLS, egress policy, secret storage, workload identity, and transport clients may instead be prerequisites or defense in depth. Research records fit and elimination evidence. System/Integration Design later composes and selects the smallest coherent architecture.

## Findings

### Executive synthesis

1. The evidence supports keeping `OUTBOUND_AUTH=oauth2-client-credentials` as the provisional portable selector, with `client_secret_basic` as its explicit minimum client-authentication method. That is the RFC 6749 interoperability floor for clients issued a password, not the strongest current security posture: RFC 9700 recommends asymmetric client authentication where the authorization server and deployment can support it.
2. The reusable responsibility is narrower than "machine identity" and broader than an HTTP header helper: one provisioned outbound dependency needs a concurrency-safe, process-local source of short-lived access tokens, sanitized failure semantics, and transport adapters for HTTP bearer authentication and gRPC per-RPC credentials. Feature code should receive the authenticated concrete or generated dependency client and should never request, cache, log, or attach tokens itself.
3. The smallest credible implementation family reuses the repository's bounded transports, typed configuration, environment-only secret channel, bootstrap lifecycle, telemetry, and profile generator, and uses the Go-maintained `golang.org/x/oauth2/clientcredentials` protocol implementation. The library is a useful primitive, not a complete repository capability: its token source has no per-call context, failed refreshes can serialize into repeated acquisition attempts, zero expiry is treated as non-expiring, missing token type can become `Bearer`, auth style can be probed, and its exported retrieval error can render authorization-server response bodies.
4. A full custom OAuth client is not justified. The standard library has the necessary HTTP, TLS, URL, time, and synchronization primitives but no OAuth client-credentials implementation; the repository has no existing token acquisition owner; and no installed dependency closes the complete flow. A small repository-owned boundary around a maintained token source remains a candidate for later design only because local cancellation, failure isolation, redaction, transport composition, and lifecycle contracts are not supplied by `x/oauth2` alone.
5. Private-key JWT changes token-endpoint client authentication but can preserve bearer consumption. OAuth mTLS client authentication also changes token-endpoint TLS; certificate-bound access tokens additionally change every resource connection. Token exchange and managed workload identity change the credential authority and often the acting/delegated principal. DPoP changes every resource request. These are not harmless flags inside the minimum pack.
6. Native or managed workload identity is preferable to stored long-lived credentials when the deployment platform and target provider already establish that trust, but there is no platform-independent identity contract in this repository. Such identity should replace or feed token acquisition through a provider/platform adapter, not make the portable secret-based pack operate a new SPIRE, mesh, Vault, or cloud control plane.
7. Research can close without a selected provider or deployment. Provider registration, accepted scopes/resources/audiences, credential issuance and rotation, sender constraints, network reachability, dependency criticality, and live rate limits remain business- or deployment-owned inputs. They must be fixed before Specification can claim provider-specific compatibility and before implementation or rollout can claim readiness.

### Standards and security contract

The table distinguishes an external requirement from the portable repository policy it supports. OAuth 2.1 remains an Internet-Draft as of 2026-08-11; it is context, not current normative authority. RFC 9700 is the current OAuth Security Best Current Practice.

| Topic | Current authority | Evidence-backed consequence for the portable capability |
| --- | --- | --- |
| Grant eligibility | RFC 6749 section 4.4 permits client credentials only for confidential clients acting on their own behalf, or under previously arranged authorization. | The pack represents the service/client itself. User delegation or on-behalf-of behavior is outside this grant and reopens the authority model. |
| Token request | RFC 6749 sections 3.2 and 4.4.2 require an authenticated TLS token endpoint, HTTP `POST`, `application/x-www-form-urlencoded`, `grant_type=client_credentials`, and optional `scope`; duplicate parameters are invalid. | The endpoint and request shape are fixed deployment configuration, never feature or request input. Do not add arbitrary token parameters to the minimum without a provider contract. |
| Minimum client authentication | RFC 6749 section 2.3.1 requires authorization servers to support HTTP Basic for clients issued a password, permits but does not recommend credentials in the request body, and forbids using more than one authentication method per request. RFC 8414 defaults omitted `token_endpoint_auth_methods_supported` to `client_secret_basic`. | Explicit `client_secret_basic` is the portable minimum. Do not use `x/oauth2` auth-style auto-detection: it can send an avoidable failed probe and can place the secret in the body. |
| Stronger client authentication | RFC 9700 section 2.5 recommends asymmetric client authentication such as mTLS or `private_key_jwt` where feasible. | Basic is compatibility, not "best security". Provider/deployment support for asymmetric methods is a named decision and migration trigger. |
| Token-endpoint trust | RFC 8414 defines HTTPS issuer metadata and token endpoint/auth-method metadata; RFC 9700 recommends clients use metadata when available. RFC 6749 requires TLS and server authentication. | Accept only deployment-fixed metadata issuer or token endpoint. Validate exact issuer binding when discovery is used; require HTTPS, normal certificate verification, fixed authority/address policy, no userinfo or fragment, no redirects, no proxy bypass, and bounded response handling. A private endpoint needs an explicit repository target policy rather than weakened TLS or DNS checks. |
| TLS baseline | RFC 9325 / BCP 195 rejects SSL and TLS below 1.2 and recommends TLS 1.3 support. Later 2026 TLS updates do not turn an existing OAuth deployment's TLS 1.2 support into an OAuth-specific protocol violation. | Use the repository/Go secure TLS baseline with certificate and hostname validation; do not add OAuth-specific insecure modes. A stricter provider or organizational TLS profile is a deployment input. |
| Access-token use | RFC 6750 section 2.1 makes `Authorization: Bearer` the standard header method and requires TLS; a client must not use more than one token transport method. | Support bearer access tokens only in this minimum. Never put tokens in URLs, query parameters, application payloads, or feature-visible configuration. |
| Privilege restriction | RFC 9700 section 2.3 recommends minimum privilege and audience restriction; RFC 8707 defines the standard OAuth `resource` indicator. A generic `audience` request parameter for ordinary client credentials is provider-specific. | Scopes, standard `resource`, and any provider-specific `audience` are registration facts. The generic pack must not invent a broad default or silently share one token across distinct dependencies. |
| Sender constraint | RFC 9700 section 2.2 recommends mTLS-bound or DPoP-bound access tokens to reduce replay of stolen bearer tokens. | Ordinary bearer remains interoperable but replayable. Sender constraint is a provider/resource capability and changes the reusable boundary as described below. |
| Token response | RFC 6749 section 5.1 requires `access_token` and `token_type`, recommends `expires_in`, defines scope response rules, requires `Cache-Control: no-store` and `Pragma: no-cache` from the server, and requires clients to ignore unknown fields. | Validate a non-empty token, supported `Bearer` type, bounded response, and usable finite lifetime. Because the generic process has no alternative lifetime authority, missing or non-positive expiry cannot safely become an indefinitely cached token; provider-specific documented expiry would need an explicit adapter. Never persist the response. |
| Renewal | RFC 6749 section 4.4.3 says a refresh token should not be included for the client-credentials grant. | Renew with a new client-credentials request. Reject or ignore refresh-token behavior rather than adding a refresh-token lifecycle to this pack. |
| Error handling | RFC 6749 section 5.2 defines error codes and permits human-readable descriptions and URIs. `x/oauth2.RetrieveError` retains the HTTP response and body and can render body content. | Treat provider details as untrusted, potentially credential-bearing data. Convert them to a closed semantic taxonomy before logs, traces, metrics, readiness, or feature errors; retain raw details only inside an explicitly protected diagnostic path if one is later authorized. |

#### Token endpoint trust rules

Stable rules supported by both the standards and current `httpclient` policy are:

- The issuer, metadata URL, token endpoint, scopes, resources/audience, and credential identity are deployment inputs. None may be derived from an inbound request, generated feature payload, token claims, or an untrusted error response.
- Discovery, when used, is bound to an exact configured issuer. A returned token endpoint is separately parsed and admitted as a fixed HTTPS target. Cross-origin metadata is not automatically same-trust; it must still pass the endpoint policy.
- The issuer value returned by RFC 8414 metadata must exactly match the configured issuer; mismatched metadata is unusable, not a hint that can retarget the client.
- Direct token-endpoint configuration does not weaken endpoint validation. The client pins the configured scheme and authority, refuses redirects, performs normal TLS hostname and chain verification, applies the selected public/private address policy before and after DNS, uses no ambient proxy, and bounds headers, body, connections, and request time.
- The Basic credential is sent only to the admitted token endpoint and never forwarded on redirect or resource calls. Token endpoint and resource endpoint are separate authorities and transport instances even when their hostnames match.
- Authorization-server metadata is preferred when the provider publishes it, because it binds the endpoint and supported authentication methods. Absence of metadata does not justify opportunistic discovery or auth-style probing.
- Minimum privilege is enforced at provisioning: one dependency does not reuse a token configured for another resource merely because issuer and client ID match.

#### Evidence-supported minimum input envelope

Research supports the following inputs without fixing a final schema: a bounded dependency identity; either an exact token endpoint or an exact metadata issuer under one selected trust mode; explicit `client_secret_basic`; client ID; client secret through the environment-secret channel; zero or more exact scopes; and, only when the provider contract requires it, one RFC 8707 `resource` or a named provider-specific `audience`. Transport timeout/bounds and public/private target class must come from repository-owned policy rather than feature code.

Arbitrary token parameters, authentication auto-detection, token/cache tuning, retries, introspection, JWT parsing, discovery fallback, and multi-provider fallback are not minimum configuration. The access token is opaque to this client even when it is encoded as a JWT.

### Runtime semantics and failure boundaries

| Concern | Research conclusion | Evidence and later proof obligation |
| --- | --- | --- |
| Cache ownership | One provisioned dependency owns one in-memory token source. No file, database, distributed, or cross-process token cache is justified. | Bearer tokens are secrets; persistence adds disclosure and consistency obligations. A global tuple-keyed cache adds identity aliasing risk. Sharing can reopen only after measured provider pressure and exact authority equivalence. |
| Expiry | Consider a token unusable before its server expiry by a small fixed safety margin. A configurable early-expiry API exists in `x/oauth2`; exposing a template knob is not justified without provider or clock evidence. | `x/oauth2` defaults to a 10-second early-expiry delta and otherwise treats zero expiry as non-expiring. Later tests must cover boundary time and clock skew without real sleeps. |
| Renewal | On-demand renewal is the minimum: a valid cached token is reused; an absent/nearly expired token causes a new client-credentials request. No refresh token and no mandatory background goroutine. | This avoids idle token churn and bootstrap/shutdown machinery. A proactive loop is justified only by an accepted readiness or latency objective. |
| Concurrency | Concurrent callers for one dependency must not cause duplicate successful acquisitions. One leader may perform acquisition; each follower needs an independently cancelable wait. | `x/oauth2.ReuseTokenSource` mutex-serializes acquisition, but `Token()` has no context parameter. Claim-scoped concurrency proof must cover success, leader failure, canceled waiters, expiry, and shutdown. |
| Cancellation | Token endpoint I/O needs a bounded provider deadline distinct from a feature caller's deadline; a canceled caller must stop waiting promptly without canceling useful process-owned work for other callers. | The current `x/oauth2/clientcredentials.TokenSource(ctx)` binds one construction context. Plain use does not propagate each HTTP request or gRPC RPC context into token acquisition. The existing inbound OIDC lifecycle demonstrates the relevant caller/provider distinction, not reusable code. |
| Provider failure isolation | A token endpoint outage must affect only dependencies that need that provider, return a sanitized stable error, and avoid turning waiting callers into a sequential acquisition storm. | `ReuseTokenSource` coalesces a successful refresh under a mutex, but after failure leaves no valid token; queued callers can each become the next requester. Later reliability design needs a bounded fail-fast/backoff policy, without serving expired tokens. |
| Retry | The portable default is no automatic token-endpoint retry. A retry can issue multiple usable tokens after an ambiguous response, and current `httpclient` does not retry a POST without its idempotency contract. | Provider-specific retry-after/backoff behavior may reopen this. Retries must remain within one provider budget and must not multiply resource retries. |
| Resource `401`/`403` | Do not transparently refresh and replay a generic resource operation. These statuses can mean wrong audience/scope/policy, and replaying a non-idempotent HTTP or gRPC operation is unsafe. | A concrete provider adapter may invalidate for the next call or safely retry a proven replayable operation. Generic feature clients retain operation semantics. |
| Multi-replica behavior | Process-local coalescing does not coordinate replicas; aligned starts or expiries can create provider bursts. This is a modeled risk, not a current measured failure. | Do not add distributed caching. Reopen jitter, proactive refresh, or platform brokerage only with replica/provider rate-limit evidence and a representative measurement. |
| Startup/readiness | Validate all static configuration at startup. Default token acquisition remains lazy. Remote auth health does not enter liveness; readiness may only consume cached state and only if the deployment declares the authenticated dependency critical. | Eager acquisition would add provider availability to deployment admission and create tokens for unused dependencies. Readiness criticality is deployment/business policy. |
| Shutdown | An on-demand source has no independent shutdown beyond bounded in-flight provider work and transport cleanup. Any future refresh goroutine must be bootstrap-supervised and joined before telemetry shutdown. | Later design must not create unowned goroutines or let process-owned acquisition outlive shutdown. |
| Long-lived gRPC streams | Per-RPC credentials are applied when a stream is created; they do not rotate metadata mid-stream. | The resource server decides whether an established stream survives token expiry. Reauthentication requires stream reconnect and is a concrete RPC/client policy, not generic token refresh. Health `Watch` reconnection must still use the same credential. |

### HTTP and gRPC integration requirements

- HTTP authentication belongs in a provider/dependency adapter that obtains a token before the admitted resource request and sets exactly one `Authorization: Bearer ...` header. It must preserve `httpclient` target policy, bounds, redirect refusal, proxy policy, retry ownership, correlation hygiene, and standard instrumentation. `oauth2.NewClient` is not a drop-in fit because it constructs its own resource client and the context-provided HTTP client is used only for token acquisition.
- Transport ordering is a Technical Design question, but the behavior is fixed here: token acquisition is not repeated per internal resource retry; a resource retry cannot forward a token to a new authority; and the auth layer cannot overwrite a caller-supplied authorization header silently.
- gRPC authentication uses the existing provider-owned `PerRPCCredentials` seam, emits `authorization: Bearer ...`, returns `RequireTransportSecurity=true`, honors the RPC caller's cancelable wait, and supplies credentials to both application RPCs and client control streams. It must not replace TLS transport credentials.
- HTTP and gRPC consume the same dependency-owned access-token responsibility only when they share the exact provider registration, resource/audience, scopes, client-auth method, and failure semantics. Similar bearer syntax alone is not enough to merge owners.
- Generated or concrete feature clients receive the authenticated transport/client at bootstrap composition. Feature code selects the named dependency and invokes its API; it does not see secret configuration, a token source, token values, refresh controls, or OAuth error bodies.
- The client treats the access token as opaque. Signature, issuer, audience, claim, and authorization validation belong to the resource server; outbound code cannot inspect a JWT-shaped token to infer lifetime, scope, tenant, or retry behavior.
- Trace propagation into a token request must not accidentally inherit a feature caller's correlation or baggage. Token acquisition needs its own sanitized dependency span/metrics context if observed; no credentials, request body, response body, token, client ID, scope/resource value, or full endpoint becomes telemetry.

### Credential-method boundary tests

| Method | What it changes | Can share the minimum bearer-consumer boundary? | Required owner/facts before inclusion |
| --- | --- | --- | --- |
| `client_secret_basic` | Token-endpoint client authentication with a symmetric secret. | Yes; this is the provisional minimum. | Provider registration, secret issue/rotation/revocation, endpoint metadata, scopes/resource/audience, egress, and restart-based rotation acceptance. |

RFC 7523 leaves some replay policy out of band; the OpenID Connect `private_key_jwt` profile requires one-time `jti` unless reuse is negotiated. | Yes for ordinary bearer resource calls; no for acquisition/config/lifecycle. | Authorization-server support/profile and registration, key custody/signer API, algorithms, assertion lifetime/audience/JTI rules, clock source, rotation and revocation. |
| OAuth mTLS client authentication | Adds client certificate selection and TLS proof at the token endpoint. | Yes only when the issued access token remains ordinary bearer. | AS metadata/aliases, certificate issuer/delivery/rotation/revocation, trust roots, target TLS policy, and bootstrap owner. |
| Certificate-bound access token | Binds token use to the certificate thumbprint and requires the same proof at resource servers. | No: every HTTP resource transport and gRPC channel must present the bound certificate. | AS and resource-server support, certificate continuity across token/resource calls, TLS resumption/rotation behavior, and verification proof. |
| RFC 8693 token exchange | Adds a subject token and optionally actor/delegation semantics; client authentication remains separate. | The resulting bearer may share attachment, but acquisition authority and principal semantics are separate. | Subject-token issuer/audience, trust and rotation, requested subject/actor/resource, delegation policy, STS support, and audit semantics. |
| Managed workload identity | Supplies a platform-attested source credential, provider SDK chain, or STS exchange instead of a stored secret. | Only when the provider returns a normal OAuth bearer for the same dependency. AWS-style credentials or direct mTLS do not. | Deployment platform, workload binding, target federation, SDK/agent availability, entitlement propagation and revocation, local-development route. |
| Direct SPIFFE mTLS/JWT | Authenticates the workload directly with an SVID. | No unless a downstream explicitly exchanges the SVID for the same OAuth bearer. | SPIFFE control plane, trust domain, attestation/registration, target acceptance, Workload API availability, rotation and federation. |
| DPoP | Creates a proof JWT per resource request and changes token type/header; it sender-constrains a token but is not client authentication. | No: it changes HTTP request signing and has no generic gRPC bearer equivalent. | AS/resource support, nonce policy, key custody, HTTP method/URI binding, replay cache, and library support. |

### Stable reusable responsibilities

The following responsibilities are stable enough for Specification to treat as common behavior without selecting package or type placement:

- Validate one immutable dependency authentication configuration and keep secret material out of YAML, generated examples, logs, errors, telemetry, readiness, and user-visible diagnostics.
- Admit one fixed token endpoint under the repository's outbound trust policy; bind discovery to exact issuer when discovery is selected; never follow redirects or use ambient proxies.
- Authenticate once with the configured method, request least-privilege scope/resource values, strictly validate a bounded bearer response and finite usable expiry, and renew with a new grant.
- Keep one in-memory token per provisioned dependency, use early expiry, coalesce acquisition, let each caller cancel waiting, bound provider work independently, prevent failure amplification, and never serve an expired token.
- Attach the token below feature code to admitted HTTP requests or existing gRPC per-RPC credentials while preserving transport TLS, target, retry, correlation, telemetry, control-stream, and shutdown rules.
- Return a closed semantic failure taxonomy that separates invalid configuration, trust/TLS, timeout/cancellation, provider unavailable, rejected client, invalid scope/resource, malformed/unsupported response, and downstream unauthorized/forbidden without carrying raw provider content.
- Emit bounded auth acquisition/cache/failure evidence under a configured dependency identity; keep liveness independent and make readiness contribution cached and deployment-controlled.
- Generate or retain the pack only when the profile selects it, record the selector in template authority, and prove both selected and stripped profiles.

Responsibilities that remain outside the reusable core are resource-operation retries, feature authorization policy, provider-specific token claims, business selection of scopes/resources, dynamic secret-store integration, provider SDK credentials, certificate or HSM control planes, token exchange/delegation, direct mTLS identity, DPoP, shared caches/brokers, and deployment manifests.

### Risks and downstream implications

| Risk | Consequence | Downstream obligation / reopen condition |
| --- | --- | --- |
| R-01. `x/oauth2` construction context is mistaken for caller context | HTTP/gRPC cancellation can leave callers blocked behind token acquisition or bind the source to a short-lived startup/request context. | Specification must state independent provider budget and caller-cancelable wait; Technical Design proves the context ownership. |
| R-02. Failed acquisition convoy | A provider outage can turn queued traffic into serial token requests and amplify dependency failure. | Specify bounded coalescing/fail-fast behavior; test leader failure and high-concurrency followers. |
| R-03. Provider error disclosure | `RetrieveError.Error()` can include provider description/URI or raw response body. | Sanitize at the credential owner before any return/log/span/metric/readiness path; add negative disclosure tests. |
| R-04. Missing expiry becomes indefinite cache | `x/oauth2` treats zero expiry as reusable forever, while RFC 6749 permits an AS to omit `expires_in` only if another expiry authority is documented. | Portable behavior must reject missing/non-positive expiry; reopen for an explicit provider adapter with another trusted lifetime source. |
| R-05. Credential sent to wrong endpoint | Redirect, auth-style probing, ambient proxy, endpoint substitution, or DNS rebinding can disclose the Basic secret. | Fixed admitted endpoint, explicit Basic, refused redirects/proxy, pre/post DNS checks, normal TLS, and trust-boundary tests. |
| R-06. Bearer replay | A stolen bearer works until expiry unless sender-constrained. | Minimize privilege/lifetime and protect telemetry/memory; record provider support for mTLS-bound tokens or DPoP as a security upgrade trigger. |
| R-07. Retry crosses authority or replays side effects | Resource `401` or transport retry can duplicate non-idempotent work or forward credentials. | Keep operation retry with concrete dependency clients; prove wrapper order and fixed authority. |
| R-08. Readiness cascade | Eager token acquisition or synchronous readiness couples deployability to an external AS and can make optional dependencies global outages. | Default lazy acquisition, cached state only, liveness independent; criticality requires owner decision. |
| R-09. Profile retention drift | A new dependency or package remains in `none` profiles, or `httpclient` is stripped while auth still needs token transport. | Extend selector validation, lock/profile authority, generated checks, and tidy-based removal in later phases. |
| R-10. Secret rotation assumes live reload | Operators may rotate the environment secret and expect an already-running process to observe it. | Document restart semantics in Specification, or reopen a separate dynamic-secret capability. |
| R-11. Long stream outlives token | A resource can terminate or reject a stream after expiry; metadata cannot be replaced in place. | Concrete streaming client specifies reconnect/resume and idempotency; generic auth only authenticates stream creation. |
| R-12. Current config-policy documentation overstates file hardening | A private-key or certificate design may assume symlink/path/permission checks that executable code does not enforce. | Use the executable secret policy as current truth and explicitly design any file credential trust before accepting it. |
| R-13. Managed identity is treated as "no credentials" | Agent, projected-token, STS, SDK, entitlement-propagation, and revocation failures disappear from readiness/operations. | Name the platform credential owner and its availability/rotation/error contract before selecting the managed path. |

### Saturation and movement evidence

The search covered repository reuse, standard library, native Kubernetes identity, installed dependencies, mature Go OAuth and SPIFFE libraries, provider SDK/default credentials, managed cloud identity, service mesh/sidecar/secret delivery, broker/shared cache, and custom code. Private-key JWT, mTLS, certificate-bound tokens, token exchange, workload identity, direct SPIFFE identity, and DPoP were classified by how they alter acquisition, principal authority, or resource transport. Additional surfaced products mapped to one of these families rather than changing the decision level.

Research is ready for Specification because every open item R1-R7 now has decision-changing evidence, a bounded unknown, and an owner/checkpoint. The leading hypothesis is the portable `client_secret_basic` pack using a maintained OAuth primitive behind one dependency-owned token/transport boundary. Specification must test that hypothesis against the first named provider's metadata and the required readiness/failure policy; it must not treat the candidate implementation or package placement as accepted architecture.
