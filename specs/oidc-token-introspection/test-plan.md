## Evidence boundary and dispositions

The current checkout is still dirty and the separately owned
`internal/infra/httpclient` refactor is not accepted authority. Its provisional
retry, instrumentation, configuration, error, and response-limit APIs are not
fixtures or proof inputs for this plan. The candidate Implementation must
refresh the accepted `httpclient` owner exactly as the Technical Design
requires. Equivalent accepted constructor names may be substituted; every
semantic falsifier below remains mandatory.

No implementation exists for this profile, so this Test Design executes no
behavioral command and makes no current-tree compile or passing-test claim.
Rows marked `planned scenario` are mandatory before local implementation
acceptance. Rows marked `non-test falsifier` are mandatory structural or
external procedures. The two `authorized residual risk` rows are not local
completion claims and remain blocking gates before a real provider is enabled.

## Proof strategy

The proof ladder stops at the smallest boundary that can observe the wrong
behavior:

- Pure endpoint, policy, JSON, NumericDate, issuer, audience, time, and identity
  admission use package unit tests with an injected fixed `now`. HTTP or e2e
  tests were rejected for these rules because they can return the right status
  while the parser or classification is wrong.
- Carrier removal, caller-visible failure parity, public-method policy,
  principal publication, metrics, stream expiry, and outer capacity use real
  HTTP/OpenAPI and native gRPC contract seams. Direct verifier calls were
  rejected because they cannot observe transport status, challenge, metadata
  removal, handler admission, or message I/O.
- Request construction, TLS, ALPN, redirect, proxy, one-attempt behavior,
  response bounds, cancellation, and idle-connection lifecycle cross a real
  loopback TLS server. A mocked `Do` was rejected because it can pass without
  TLS, protocol negotiation, transport header enforcement, redirect policy, or
  connection cleanup.
- The direct `httpclient` header tests remain provider-neutral. Provider tests
  cannot replace them because an adapter-side body limit could falsely appear
  to prove transport response-header enforcement.
- Static initializer output is proved in disposable generated checkouts;
  source-text presence in the template is not an oracle for physical absence,
  dependency removal, generated OpenAPI, lock readback, or repeatability.
- One local runtime-image smoke proves generated executable composition and
  readiness behavior. It does not replace the lower falsifiers and makes no
  live-provider compatibility claim.

## Deterministic controls and fixtures

- Use one fixed UTC instant with clearly inside/outside 30-second-skew cases;
  boundary cases use exact instants rather than sleeps. Keep `sub` and
  `client_id` as independent fields in expected principals.
- Use package-local table fixtures for raw JSON so duplicate members, trailing
  values, exponent forms, fractional numbers, wrong types, whitespace, and
  unknown members are not normalized by a test struct before parsing.
- Use an unexported loopback TLS provider with explicit roots, request/call
  counters, per-call barriers, captured method/URL/headers/raw form body,
  connection-state observation, and cleanup registered before serving. Force
  HTTP/1.1 or TLS ALPN HTTP/2 per scenario and assert the negotiated protocol.
- The HTTP/2 header-size falsifier sends high-entropy response fields whose
  decoded header-list size exceeds the configured limit plus protocol
  accounting margin. An under-limit control must succeed on the same server.
- Cancellation fixtures signal `request received` before canceling or expiring
  the caller. The provider-owned timeout uses a handler blocked on request
  context and the real fixed five-second bound; an outer seven-second guard
  detects a hang. This is one bounded wall-clock case, not a timing assertion.
- Capacity fixtures use barriers and atomic call/peak counters. HTTP sets
  `max_in_flight=1`; gRPC admits exactly 256 protected RPCs before attempting
  the 257th; a combined fixture admits one HTTP and one gRPC call concurrently
  to disprove a hidden shared limiter.
- Disclosure fixtures use unique canaries for token, secret, endpoint, issuer,
  audience, subject, client ID, provider body, network text, and parser text.
  Scan caller responses, formatted errors, captured logs, in-memory metric
  attributes, trace output, startup/config diagnostics, and runtime-image logs.
- No test depends on a public network, ambient proxy, wall clock, provider
  account, database, retry, cache, scheduler luck, or test order. Environment
  mutation and fixed-port cases must not use `t.Parallel()`.

## Validation ladder

Implementation first runs the exact focused commands in the rows it changes.
The fixed implementation candidate then runs, in order:

1. `go test -count=1 ./internal/authntrust ./internal/infra/httpclient ./internal/infra/bearerauthn ./internal/infra/oidcjwt ./internal/infra/oauthintrospection ./internal/config ./internal/infra/http ./cmd/service/internal/bootstrap`
2. `go test -count=1 -race ./internal/infra/bearerauthn ./internal/infra/oauthintrospection ./cmd/service/internal/bootstrap`
3. `go test -count=5 -shuffle=on ./internal/infra/bearerauthn ./internal/infra/oauthintrospection ./internal/infra/httpclient`
4. `make openapi-check`
5. `make lint mod-tidy-check`
6. `make template-init-check`
7. `make runtime-image-build RUNTIME_IMAGE=service:oidc-introspection-test`
8. `make check`

Race and shuffle are instrumentation over the named concurrency/lifecycle
scenarios, not substitutes for them. A cached result, zero-match `-run`, skipped
Docker path, unavailable generated fixture, or current unrelated dirty-tree
compile failure is not passing evidence. The acceptance report must state the
exact candidate identity, executed test names/counts, command results, and any
broader unrelated blocker without using it to waive focused proof.
