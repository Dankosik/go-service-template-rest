## Evidence boundary and dispositions

The inbound capability has no implementation candidate. The checkout is dirty,
and `specs/inbound-webhooks/` is currently untracked; neither fact is behavior
evidence. No behavioral command is executed or claimed passing in Test Design.
`planned scenario` rows are mandatory local implementation proof. `non-test
falsifier` rows are mandatory release or adopter procedures that local tests
cannot replace.

The current repository already supplies the relevant harness owners:
`pgtest.Migrated` for one isolated real PostgreSQL database per test, River
integration and jobs-worker process patterns under `./test`, generated OpenAPI
runtime checks, initializer disposable checkouts, and runtime-image smoke.
Those owners are reused; no second database, queue, clock, retry engine, or test
framework is proposed.

## Proof strategy

- Pure identifier, configuration, manifest, signature, registry, classification,
  state-transition, metric-vocabulary, and buffer-budget rules use package tests
  with fixed inputs. HTTP or process tests were rejected for these rules because
  a correct status or terminal job can hide the wrong local classification.
- Raw-byte identity, validation order, public security, CORS absence, empty
  `204`, Problem mapping, `Retry-After`, middleware admission, timeout, and `431`
  use the generated router or a real loopback `net/http.Server`. Direct receiver
  tests cannot observe the wire contract or listener boundary.
- Receipt/job atomicity, composite-key arbitration, visibility, constraints,
  and migration lifecycle use real PostgreSQL behind the integration tag. A
  mocked transaction was rejected because it can pass without atomic commit,
  locking, or read-committed visibility.
- River recovery, attempts, persisted errors, and disclosure sinks use the real
  River schema/client and, where process loss is the claim, a built jobs-worker
  subprocess. A direct `Work` call cannot prove durable recovery or what River
  persists and emits.
- Initializer absence is proved in disposable initialized checkouts. Grepping the
  source template cannot prove physical removal, retained shared dependencies,
  generated drift, the exact lock, or repeatability.
- No latency, throughput, or allocation claim is accepted. The selected request
  memory rule is structural: at most
  `max_in_flight * max_body_bytes * copies_per_request`, compared with the
  existing GC-limit budget. A benchmark is rejected because `-benchmem` cannot
  prove live in-flight heap or deployment capacity; the arithmetic/log contract
  is local proof and runtime capacity remains an external gate.

## Deterministic controls

- Signature cases use fixed UTC Unix second `1700000000`, the reviewed
  compatibility vector, exact `-300s` and `+300s` accepted boundaries, and
  `-301s` and `+301s` rejections. No test uses wall-clock sleeps.
- Raw bodies are byte literals, including insignificant whitespace, invalid JSON,
  a one-byte body mutation, and exactly/over-limit payloads. Tests do not marshal
  an expected struct before verification.
- Concurrency uses start barriers and result channels. Every contender enters
  before release; database rows and River jobs are read after all callers join.
- Store, decoder, handler, terminal-update, and panic cases use distinct canaries
  and counters. Assertions inspect durable rows, `river_job.errors`, captured
  logs, spans, and metric attributes; returned status alone is never the oracle.
- Process tests use `waittest` events, River subscriptions, or database state
  with bounded contexts. Polling observes state only; elapsed time is not a
  correctness oracle.
- Every Docker-backed command sets `REQUIRE_DOCKER=1`. A skipped test, cached
  result, or zero-match `-run` is not evidence; acceptance must report the named
  tests that actually ran.
