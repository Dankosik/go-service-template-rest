# OIDC/JWT Authentication Test Plan

status: ready

## Proof boundary and fixture authority

This plan proves the ready specification and design at the narrowest owner.
It does not use a live identity provider, wall-clock sleeps, an unsigned fake
identity, or source-string presence as a behavioral oracle.

Implementation creates these capability-owned fixtures:

- two fixed test-only RSA-2048 private keys and public JWK representations under
  `internal/infra/oidcjwt/testdata`; production code cannot import or discover
  them;
- strict Discovery and JWKS response builders whose default documents derive
  from the accepted issuer, JWKS URI, and key-admission rules;
- a fake clock and event-driven timer controlled only by tests, plus an
  unexported single-request HTTP dependency implemented in the consumer package;
- a token builder that always creates a real compact RS256 JWS and mutates one
  behavior-significant dimension per case;
- an in-memory OTel meter provider and captured bootstrap logger, with a common
  poison marker inserted into every untrusted input surface;
- a synthetic secured OpenAPI operation using the production router and a TLS
  `bufconn` gRPC service using the production interceptor chain.

Fixed fixture bytes make token/JWKS inputs reviewable and repeated tests stable;
the oracle is still the verifier or transport result, not fixture text. Fake
time advances timers synchronously and waits on owned events. Real-time
deadlines are outer liveness diagnostics only.

## Non-test falsifiers and retained risk

**NT-01 — Replay boundary.** Review `docs/authentication.md` and the generated
profile guide to confirm they state that bearer tokens remain replayable until
expiry and that this capability provides no replay store, DPoP, or mTLS-bound
token. Then inspect the production dependency graph for replay/session storage.
This is a deliberately retained risk authorized by the ready specification;
reopen Specification if replay prevention becomes an accepted outcome.

**NT-02 — evidence boundary.** Record exact Go version, selected go-jose module
version/checksum, `go mod verify`, current `govulncheck`, `gosec`, OpenAPI drift,
profile lane, and Git diff/status evidence. These establish only the recorded
revision/tool/database state. A later dependency advisory, standards change,
Go upgrade, or profile-script change reopens the matching Research, Design, or
Validation owner.

## Planning handoff and stop rule

Implementation must place TD-01 through TD-20 beside their narrow production
owner, then run TD-21 only after the deterministic shared-state scenarios pass
without `-race`. TD-18 and TD-19 are one serialized generator task because each
creates several temporary Go builds; they must not overlap broad Go/Docker
gates. NT-01 and NT-02 are closeout tasks.

No required fixture or command is unavailable. Every mandatory user case maps
to at least one row, and each row maps back to accepted behavior, a preserved
invariant, or a recorded evidence-boundary risk. Independent QA review must
return `PASS` before Planning.
